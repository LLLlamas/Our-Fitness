## Wrist → phone fix: `sendMessage` first, `transferUserInfo` fallback, action ids (2026-11-20) — validation record
Follow-up to the Phase 0 FAIL above, on `plan/cardio-newer-watch` from `a992339`. Fresh pair made for this run and deleted afterwards (`Cardio-Fix-iPhone` iPhone 17 / iOS 27.2 + `Cardio-Fix-Watch` Series 11 46mm / watchOS 27.2, `simctl pair`). Same build and signing as Phase 0 (Debug, `-derivedDataPath ./build/DerivedData-cardio`, ad-hoc `CODE_SIGN_IDENTITY=-`). The watch app was installed directly on the watch sim. Phone and watch were driven by throwaway UI-test harnesses kept outside the repo.
- **Root cause (reproduced on the unchanged build): the simulator's IDS layer drops a watch `transferUserInfo` before it reaches the app.** It is not app code. With the phone app running in the foreground, the watch's `wcd` sent each action as `(IDS) Framework Send Resource At URL` and logged `result: SUCCESS`. On the phone, `wcd` logged `[com.apple.IDS_SIMD] calling handler for serviceName com.apple.private.alloy.watchconnectivity received message … 3531 bytes`, then `[com.apple.IDS:_IDSService] … Calling out to IDSService delegate <WatchConnectivityDaemon> for incomingMessage if it responds` → `doesRespondToSelector? NO` (and the same for `incomingMessage with context`). Nothing followed: no `WCDPayloadSendType` line and nothing in the app process. So the selector that returned NO is IDS's optional `incomingMessage` callback on the phone's WatchConnectivity daemon, not on `WatchSyncService`. The simulator shim delivers the file-resource transfer as a plain IDS message, which `wcd` does not handle. Protobuf traffic in the same direction was decoded normally (`DaemonsClientsInformation`, `FirstUnlockAck`).
