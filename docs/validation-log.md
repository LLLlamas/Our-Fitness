Sources checked this session (what was and was not confirmed):
- Alfredson 1998, *Am J Sports Med* 26(3):360 — abstract: 15 recreational athletes, 12 weeks, all back to full running. 3 × 15 twice daily is confirmed from Beyer 2015's description of the ECC arm, not from Alfredson's own text.
- Beyer 2015, *Am J Sports Med* — full text read: 58 patients, 12 weeks, ECC = 3 × 15 slow reps, straight + bent knee, twice a day, 7 days/week, ~3 s/rep; HSR = 3×/week, 3 exercises, 3–4 sets, 15RM wk 1 → 6RM wk 9–12, 3 s up + 3 s down; adherence 92% vs 78%; similar outcomes, held at 52 weeks.
- Kongsgaard 2009, *Scand J Med Sci Sports* 19(6):790 — full text read: 39 men, decline squat = 3 × 15 slow reps on a 25° board, twice daily, 12 weeks, ~3 s/rep; HSR good short- and long-term, injections poor long-term. The decline-squat arm's own outcome numbers were not read.
- Rio 2015, *Br J Sports Med* 49:1277 — abstract only (6 players; 7.0 → 0.17 vs 6.3 → 3.8 on the single-leg decline squat; strength +18.7%). The hold dosing (sets, seconds, %MVC) was NOT confirmed, so the app states none. The Spanish squat itself was not the tested exercise.
- Bohm 2015, *Sports Med Open* — abstract: 27 studies, stiffness SMD 0.70.
- Cullinane 2014, *Clin Rehabil* — via search summary only (12 studies, 8 RCTs; supports eccentric work, heterogeneous). Not opened.
- Nordic hamstring curl, tibialis raise and pogo hops were left out: Nordic is a hamstring-muscle injury drill (and its meta-analysis is disputed), the other two had no source checked.
METs reuse Calf raise 3.5 / Squat 5.0 / Wall sit 4.0 / Bicep curl 3.5; none were checked against the Compendium (open item 10 in [health-data-audit](health-data-audit.md)).

## Wrist → phone fix: `sendMessage` first, `transferUserInfo` fallback, action ids (2026-11-20) — validation record
Follow-up to the Phase 0 FAIL above, on `plan/cardio-newer-watch` from `a992339`. Fresh pair made for this run and deleted afterwards (`Cardio-Fix-iPhone` iPhone 17 / iOS 27.2 + `Cardio-Fix-Watch` Series 11 46mm / watchOS 27.2, `simctl pair`). Same build and signing as Phase 0 (Debug, `-derivedDataPath ./build/DerivedData-cardio`, ad-hoc `CODE_SIGN_IDENTITY=-`). The watch app was installed directly on the watch sim. Phone and watch were driven by throwaway UI-test harnesses kept outside the repo.
- **Root cause (reproduced on the unchanged build): the simulator's IDS layer drops a watch `transferUserInfo` before it reaches the app.** It is not app code. With the phone app running in the foreground, the watch's `wcd` sent each action as `(IDS) Framework Send Resource At URL` and logged `result: SUCCESS`. On the phone, `wcd` logged `[com.apple.IDS_SIMD] calling handler for serviceName com.apple.private.alloy.watchconnectivity received message … 3531 bytes`, then `[com.apple.IDS:_IDSService] … Calling out to IDSService delegate <WatchConnectivityDaemon> for incomingMessage if it responds` → `doesRespondToSelector? NO` (and the same for `incomingMessage with context`). Nothing followed: no `WCDPayloadSendType` line and nothing in the app process. So the selector that returned NO is IDS's optional `incomingMessage` callback on the phone's WatchConnectivity daemon, not on `WatchSyncService`. The simulator shim delivers the file-resource transfer as a plain IDS message, which `wcd` does not handle. Protobuf traffic in the same direction was decoded normally (`DaemonsClientsInformation`, `FirstUnlockAck`). Phone state after water, quick set and meal shortcut was unchanged: water 0 / 80 oz, 525 cal. `WatchSyncService` was the live delegate the whole time (`WCSession` logs name `OurFitness.WatchSyncService`).
- **Fix.** The watch sends by `sendMessage(_:replyHandler:errorHandler:)` while `isReachable`, and falls back to `transferUserInfo` when unreachable or when the message errors. The phone implements `session(_:didReceiveMessage:replyHandler:)`, replies at once, and applies the action through the same `apply`. Each action carries a UUID under a sibling dictionary key (`WatchActionMessage`), so `WatchAction`'s JSON is unchanged and no schema bump is needed. The phone keeps the 64 newest applied ids (`RecentActionIDs`, persisted) and drops repeats. The watch also logs `didFinishUserInfoTransfer` errors.
- **Simulator after the fix: PASS, each action applied exactly once** (phone values read from the accessibility tree and screenshots):
  - Water Sip 4 oz: 0 → 4 oz.
  - "+1 min Carried Baby" quick set: phone row "—" → "1 min", 1 set.

  - End on the watch: the live card cleared and one history row appeared, "Basketball game · ~22 cal · 3 min".
  - Phone app terminated, then wrist water: the message woke the phone app in the background (new pid, reply `kNoErr`) and water went 4 → 8 oz.
  - Phone app log: six `handleDictionaryMessageRequest` lines, six successful replies, and zero "duplicate wrist action" lines. The watch logged no `sendMessage failed`.
