# Map: Apple Watch

The watch companion app (WatchConnectivity sync, wire format, watch screens, on-wrist workouts).

> Rows describe current code. **Update the matching row in the same commit as the code it describes** — a stale row is worse than none. Index of all maps: [../../CLAUDE.md](../../CLAUDE.md) → "Find it fast".

| Goal | File(s) |
|---|---|
| Watch companion sync | `Services/WatchSyncService.swift` + `Shared/WatchSyncPayload.swift` — `WatchConnectivity`: `updateApplicationContext` (phone→watch push), `transferUserInfo` (watch→phone actions). Watch is a thin client with no local SwiftData; phone is source of truth |
| Adding anything to the watch's data | `Shared/WatchSyncPayload.swift` → `WatchSnapshotEnvelope`. **ONE envelope under ONE context key — never add a second key.** `updateApplicationContext` replaces the whole dictionary, so a second key silently clobbers the first. Phone builds it in one pass in `WatchSyncService.pushSnapshot`; give any new field a default in the hand-written `init(from:)` (a memberwise default is ignored by synthesised `Codable` for a missing key, which would break older payloads wholesale). **Only `WatchSnapshotEnvelope` and `TodaySnapshot` have that hand-written decoder.** The nested element types — `ReminderSnapshot`, `QuickLogExercise`, `MealShortcut`, `LiveSessionSnapshot` — use synthesised decoding, so a new NON-Optional field on any of them is a breaking wire change: the throw propagates out of `decodeIfPresent([…])` and costs the watch the whole envelope (today's numbers included), not just that element. Add it as Optional, or bump `currentSchemaVersion`. Tests: `OurFitnessTests/WatchSyncPayloadTests.swift` (incl. the two tests pinning that boundary) |
| Wrist → phone mutations | `WatchAction` in `Shared/WatchSyncPayload.swift`, applied by `WatchSyncService.apply`. The watch sends an **id**; the phone re-resolves real macros/calories — never trust numbers off the wire, a stale snapshot must not be able to write wrong data |
| Watch app (thin client, no local SwiftData) | `OurFitnessWatch/` — root `OurFitnessWatchApp.swift` is a 3-tab `TabView`: `WatchTodayView` (glance + water quick-log) · `WatchTrainView` (`WatchLiveSessionView` + `WatchQuickLogView`) · `WatchMealsView` · `ReminderListView`/`ReminderDetailView`. State in `WatchSyncStore.swift` — [docs/watch-app-setup.md](../watch-app-setup.md) |
| What may appear in the watch quick-log | `Services/WatchSyncService.swift` → `quickLogExercises` filters to exercises ONE TAP CAN RECORD CORRECTLY. `.logQuickSet` writes `reps:` and no typed weight — the wrist has no weight input — so compound/isolation lifts (per-set weight) and isometric exercises (a hold is `{reps:1, holdSeconds:N}`) are excluded: a wrist `+1` on a barbell press was logging a weightless rep into training volume. The filter is `ExerciseDTO.isOneTapLoggable`; fixed-`loadLb` movements (the starter movements) pass it. For those, the PHONE resolves the exercise's `loadLb` from the stored exercise (never off the wire) and stamps it as the row's `weightLb`, with the quick-set's calories from `CalorieEstimator.caloriesForSet(…loadLb:)`; no wire change. A wrist log never toasts a new best, and the wrist has no "last time" label (it would need a new Optional field on `QuickLogExercise`). Re-adding either exclusion needs a wire field AND an input affordance, not just lifting the filter |
| An empty watch screen must not claim empty phone data | Before the first sync the watch knows nothing, so every empty state branches on `store.hasSynced`: synced → "No movements yet / Add … on your phone", not synced → "Not synced yet / Open Our Fitness on your iPhone". `WatchTodayView`, `WatchQuickLogView`, `WatchMealsView`, `ReminderListView` all do this |
| …nor present an OLD day's data as today's | `WatchTodayView.staleNotice` — the phone pushes only on activation/foreground/mutation, so a watch opened on a morning the phone hasn't been touched holds yesterday's numbers under a "Today" title. `WatchSyncStore.snapshotGeneratedAt` (the already-on-wire `generatedAt`; nil-guards the `.distantPast` an older payload decodes to) drives one notice, shown ONLY once the snapshot predates today — a DAY boundary, matching the `Dates.dayKey` the numbers are folded on. A same-day snapshot gets no row: there's no wrist-side refresh to offer and a permanent timestamp above the hero number is noise at 40mm |
| Watch target extra sources | `project.yml` → `OurFitnessWatch.sources`: `LiveSessionState.swift`, `ActivityCatalog.swift`, `CalorieEstimator.swift`, `Shared/WatchSyncPayload.swift` (mirrors `OurFitnessTests` compiling `Domain/` directly). Of those, `LiveSessionState.swift` is currently referenced by the watch only in comments — `WatchLiveSessionView` re-derives elapsed from `LiveSessionSnapshot.startDate` because the wire snapshot has no `profileId`. **Each must stay Foundation-only with no other Domain type** or it drags the rest of Domain onto the wrist — that's why `CalorieEstimator`'s exercise-aware overload lives in `Domain/ExerciseCalories.swift` |
| On-wrist workout / heart rate | `OurFitnessWatch/WatchWorkoutSession.swift` — `HKWorkoutSession` + `HKLiveWorkoutBuilder`. `startWorkout` has exactly ONE caller, `ActivityPickerView.start` in `WatchLiveSessionView.swift` (the Start tap), and `endWorkout` exactly one, `EndSessionButton`; that pairing is the whole of hard rule 4 on the wrist, since `startWorkout` is also the only place watch HealthKit authorization is requested (uncatchable-NSException rule). Additive telemetry: the phone still stores the deterministic MET estimate, and the runner shows the sensor bpm *alongside* it rather than instead of it. Needs `OurFitnessWatch.entitlements` + `WKBackgroundModes: workout-processing` + a HealthKit-enabled watch profile |
