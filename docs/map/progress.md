| Show/hide trackers | `Features/Progress/EditTrackersSheet.swift` — `AppStorage "progressStats.\(profileId)"`. Default set = `StatKind.isDefault` (one set for every goal): weight / steps / Weekly Reps (`StatKind.trainingVolume`) / resting HR / blood pressure / Cardio Fitness (`StatKind.vo2Max`, owner decision 2026-11-20) / Cardio Minutes (`StatKind.cardioMinutes`, owner decision 2026-11-20) — trackers the app fills itself, plus BP as the one cheap self-measure; BMI (duplicates Weight) and everything needing calipers, a tape or a lab starts hidden. `ProgressTabView.enabledSet(body:markers:)` then re-adds any tracker that already `hasLoggedData`, so shrinking the default never hides a card someone was filling in. A stored CSV always wins. Two exceptions, once per profile each, run in this order from `.onAppear`: `ProgressTabView.addVO2TrackerOnce` (UserDefaults flag `progressStats.vo2MaxAdded.v1.<profileId>`) then `addCardioMinutesTrackerOnce` (own flag `progressStats.cardioMinutesAdded.v1.<profileId>`, so it also runs for profiles whose VO₂ flag is already set). Each appends its tracker to a customized CSV via `CardioFitness.enabledTrackers(_:adding:)` ("none" → just that tracker, so a "none" profile ends as `vo2Max,cardioMinutes`; empty left alone, the defaults include both); hiding one afterwards sticks. Tests: `CardioFitnessTests`. |
| Stat detail sheet (chart + entries + log) | `Components/StatDetailSheet.swift` — ONE sheet for every tracker. Metric-specific bits come in as slots (`headline`, `chartOverride`, `logOverride`, `footer`) plus `validate` / `showsEntries` / `minChartPoints` / `detents`; `StatDetailRow` is the shared label/value row. Weight (wheel picker), Body fat, BMI, Blood pressure, Weekly reps and Cardio fitness in `ProgressView.swift` are all thin hosts over it — never write another bespoke detail sheet |
| Training volume (tracker title "Weekly Reps") | `StatKind.trainingVolume` in `Features/Progress/ProgressView.swift` (raw value unchanged — the enabled set is a persisted CSV; only the title/unit changed). Value = reps this week, unit "reps · this week", chip "+N vs last wk"; shows 0 beside last week's total when this week is empty. Math: `Domain/TrainingHistory.swift` → `repsInWeek(_:exercises:weeksAgo:now:)` / `weeklyRepCounts(_:exercises:weeks:now:)` (Monday ISO weeks; rep exercises only — holds, minutes and unknown exercises excluded; a +1 tap counts its reps, not 1 "set") and `RepHistory.weeklyReps(sets:exercises:now:)` for last week, the one own-history note (`WeeklyNote`: approaching / passed / best week / first week back; copy `RepHistory.noteText`) and the per-exercise split. Detail = `WeeklyRepsDetailSheet` (a thin `StatDetailSheet` host): big number, last week, the note, "This week by exercise"; its ⓘ (`WeeklyRepsInfoSheet`) explains that research counts hard sets per muscle, so a reps total can't say "enough", and gives the ~80–120 reps ≈ 10 hard sets rule of thumb labelled as an estimate (the 10-set figure is unverified against the papers). The weekly-reps once-per-week TOAST is a rep-counter/`ExercisesCard` thing — see the Train map. `TrainingSummary` memoises the weekly and strength folds per data change. Tests: `TrainingHistoryTests`, `RepHistoryTests` |
| Cardio fitness (VO₂ max) tracker | `StatKind.vo2Max` (title "Cardio Fitness", unit "VO₂ max") in `Features/Progress/ProgressView.swift`, backed by `HealthMarkerKind.vo2Max` (`"vo2_max"`, ml/kg/min) synced from Health (see the Settings/HealthKit map). Read-only: `canLog` false (now an exhaustive switch, as is `markerKind`), `save` ignores it. **Never labelled:** no range line, no tint (`statusTint` returns nil), no `markerMeaning`, no target (plan §1, §9.1; pinned by `CardioFitnessTests`). Card chip and sheet note = own history only: `Domain/CardioFitness.swift` → `vo2Trend(samples:now:)` (latest vs the newest estimate ≥ 56 days earlier; ±2.0 = "about the same", the plan's noise copy rule, not a sourced figure; one reading → no verdict), `chipText` / `noteText`. Detail = `VO2MaxDetailSheet` (thin `StatDetailSheet` host): value + "estimate", `CardioFitness.asOfLabel` ("as of Nov 18", date only — marker dates are day keys), plain gloss, chart, accuracy footer with Apple's 14–65 range (`CardioFitness.supportedRange`). Empty state never says "denied"; it offers the existing Connect flow (`connectHealth` → `connectAndPersist` → `syncFromHealth`, button tap only). ⓘ `VO2MaxInfoSheet`: what it is, how to read it, base-building guidance, the single dizziness line (plan §1.2, §5). Plan: `docs/cardio-fitness-plan.md`. Tests: `CardioFitnessTests` |
| Cardio minutes tracker | `StatKind.cardioMinutes` (title "Cardio Minutes", unit "min · this week") in `Features/Progress/ProgressView.swift` — Progress only, never `StepsCard` (plan §7 Q3). Derived: `canLog` false, no `markerKind`, no tint, `save` ignores it, `hasLoggedData` false, on by default. Math: `Domain/CardioFitness.swift` → `weeklyMinutes(activities:legacy:health:now:)` — Monday ISO weeks, each session in the week it **started**, 12-week `series`; sources = logged `ActivitySessionDTO`s whose id is in the explicit allow-list `cardioActivityIds` (every catalog activity except Pilates / yoga / stretching, which are `nonCardioActivityIds`; a test fails if a catalog id is in neither; unknown ids don't count), **all** legacy `CardioSessionDTO` rows (`countsAsCardio(_:)`, exhaustive), plus Health workouts (see the Settings/HealthKit map) of a cardio `WorkoutKind` that are **not** from `ownBundleIds` (`com.ourfitness.app`, `com.ourfitness.app.watchkitapp`) and **not** overlapping one counted logged session by more than half the workout's wall-clock length (`overlapsLoggedSession`). Logged spans are `date … date + minutes`; a `LogPastSessionSheet` row carries the logging time, so the overlap rule can't catch it — the ⓘ says not to re-log Apple Workout sessions. Health minutes = `HKWorkout.duration` (clock length if 0). One note, own history only (`MinutesNote`: approaching ≥ 75% / passed / first week back; no "best week" — never push, plan §1): `minutesNoteText` → "10 min to match last week" / "+8 vs last week" / "First week back". Card: this week (0 beside last week, nil if both empty), chip "±N vs last wk". Detail = `CardioMinutesDetailSheet` (thin `StatDetailSheet` host): big number, last week, note, weekly chart, "This week" split Logged here / From Apple Health; with no Health workouts in the window a calm re-Connect hint + button (`connectHealth`, tap only; never "denied"). ⓘ `CardioMinutesInfoSheet`: what counts, both dedupe rules, minutes never add to burn, not Apple's exercise minutes. Tests: `CardioMinutesTests` |
| Strength card (every trained exercise) | `strengthCard` + `StrengthEntry` in `Features/Progress/ProgressView.swift` — hidden until something is logged; lists EVERY trained exercise, most recently trained first (top 5 + "Show all N"), each row showing the figure for its shape: weighted lift → estimated max (`≈`, labelled "estimated max"; Epley `weight × (1 + reps/30)` over sets of 1–`StrengthProgress.maxReps` (12) reps) from `Domain/StrengthProgress.swift` → `lifts(sets:exercises:now:)` (only `tracksPerSetWeight` exercises; `gainLb` = best estimate in the last 28 days minus the best before them, **can be negative** — printed plainly as "−N lb · 4 wk" in the neutral colour; nil for a lift not trained in the window or newer than it; `recentMaxLb` is the window best); bodyweight or a lift with no countable weighted set → best reps in a day; fixed-load movement → best reps in a day at its current load; `.duration` → best minutes in a day; hold → longest hold. A row is its own button (a plain `Card`, not a `PressableCard`, so each row gets its own tap) and opens `ExerciseProgressSheet` (see the Train map). Fixed-load rows are included via their stamped `weightLb`, but `StrengthProgress` still filters on `tracksPerSetWeight`, so they never get an Epley estimate. Tests: `StrengthProgressTests`, `RepHistoryTests` |
| Weekly sets per muscle + "what to add" tips (shown under the Strength card) | `Domain/MuscleVolume.swift` → `weekly(...)` / `recommendations(rows:equipment:)`. Target 10 sets/week per group, "a target to reach, not a proven threshold", no upper limit (Schoenfeld, Ogborn & Krieger 2017; see `docs/health-data-audit.md`). Core, forearms, traps, lower back and hip flexors map to no group; every logged resistance set counts |

| Tape measurements (frame size: waist, shoulders, chest, arm, thigh) | `StatKind` in `Features/Progress/ProgressView.swift` — ONE code path for all five via `StatKind.tapeIn` (a `WritableKeyPath` into `BodyMetricDTO`); values stored in canonical inches on `BodyMetricDTO.{waistIn,shouldersIn,chestIn,armIn,thighIn}` (+ `BodyMetricModel`), converted at the UI boundary. New StatKind cases are appended last (the enabled set is a persisted CSV). All start hidden (`isDefault` false) and re-appear automatically once logged. The four new columns are optional/additive and shipped WITHOUT a schema version bump (same pattern as earlier optional fields; container opens `AppSchema.current` directly). Upgrade verified on the simulator — see the Oct 2026 validation record |
